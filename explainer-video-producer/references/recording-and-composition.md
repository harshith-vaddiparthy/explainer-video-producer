# Genuine recording and composition

Use this when a beat teaches a product interaction, code workflow or visible result. A diagram can explain a mechanism; it cannot prove that a button was clicked or a file was saved.

## Prepare a recordable demonstration

Verify the requested product and current UI before dependent narration. Rehearse a coherent start-to-result path with authorized, harmless example data. Record prerequisites, starting state, input, action and expected observable result. Use names that describe the work rather than internal production IDs.

Use the real application for the requested demonstration. If access fails, report the specific missing capability and continue independent work. A fabricated interface is not a recording of that application. Authored mockups are useful only when the brief explicitly calls for them and their status is clear.

If teaching inside the same app used to coordinate production, isolate the teaching workspace and recordings from personal conversations, memory and credentials. A new browser tab is not a filesystem or tool-permission boundary. Use the environment's authorized recording route and account rules; this skill does not override service-specific access requirements.

Capture a short test before a long take. Check the encoded image, dimensions, frame rate, text size, native cursor treatment and permission dialogs. Hide unrelated sidebars and notifications using native controls where possible. Keep meaningful application text, prompts and outputs readable.

## Capture the evidence chain

For each practical beat, retain enough genuine footage to establish:

1. The relevant initial state and input.
2. The actual action, including any permission interaction.
3. The observed result.
4. A useful verification or interpretation of that result.

Preserve chronological causality. A later rerun of a checker cannot be passed off as its earlier result. Keep failed takes and retakes identified privately. If a model succeeds first try, teach why the result is correct; do not manufacture a failure to match a drafted script.

Save a source ledger with file hash, capture identity, useful time ranges, exclusions and what the range proves. Distinguish native screen recording, recorded model output rendered as animation, and authored explanatory visuals.

## Cursor and timing

Prefer recorded cursor events or the native captured pointer. Save event timestamps and the capture coordinate system. If rendering an enhanced pointer, transform coordinates through the same crop, scale, offset and time mapping as the recorded screen. Preserve clicks, pauses, drag paths and targets.

Use modest interpolation only between recorded motion samples. Avoid inventing clicks, double cursors, motion through discontinuous cuts or a pointer that highlights the next control before the narration introduces it. Inspect clicks in the final encode, including approval buttons and small targets.

Build the timeline around semantic anchors: introduce the action, show it, allow inspection, interpret the result. Preserve useful typing and causal steps. Remove irrelevant waits with an honest cut; keep a changed app state understandable after the cut. When editing source time, edit cursor timing with it.

A reading hold needs something worth reading and enough time for the intended audience. An unchanged app backdrop is not a demonstration merely because it is on screen. Repeated source ranges require a clear recap purpose; do not loop them to reach a duration or visual quota.

## Compose for comprehension

Use the configured compositor or the project's existing render stack. If HyperFrames is installed and selected, read its entrypoint and composition contract; otherwise use a suitable existing editor or FFmpeg workflow. The public skill does not require a particular compositor.

- Set canvas, aspect ratio and frame rate from the brief. Keep critical controls and text legible at the expected viewing size.
- Use diagrams for relationships, invisible flows or comparisons; use screen recordings for actions and evidence. Switch when the viewer's question changes, not because a time allocation is exhausted.
- Introduce a new app or conceptual view with one orienting sentence. State what to notice before a dense screen or multi-part diagram appears.
- Place the avatar in a tested safe region. Check its frame against every important dialog, result and label. Size the display card independently from generation resolution.
- Use concise labels and annotations that explain the current idea. Treat subtitles as a separate brief choice; application text and diagrams are not subtitles.
- Keep a source range and timing map for each scene. Round cumulative frame boundaries rather than rounding each duration independently and accumulating drift.

Preview actual exported frames and motion, not just the composition source. A technically valid crop can still hide a control; a correctly timed cut can still outrun the explanation.
